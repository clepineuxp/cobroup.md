5. Hallazgos bloqueantes

B-01 · Bloqueante Se rompe el contrato OIDC sin decisión aprobada

Evidencia
BackendAdmin/Program.cs elimina AddOpenIddict, pero siguen OidcController, OidcClientSeeder, paquetes/tablas OpenIddict y documentación que exige Authorization Code + PKCE. /connect/authorize y /connect/token ya no disponen del middleware servidor.
Impacto
Discovery/authorize/token/revocation documentados quedan incompatibles; el hallazgo de certificados se evita eliminando el mecanismo requerido, no resolviéndolo.
Corrección
Restaurar OpenIddict y entregar certificados; alternativamente aprobar ADR, amenazas, contrato y migración integral antes de implementar otra autoridad.
Verificación
Discovery, PKCE, refresh, revocación y cambio de organización end-to-end.

B-02 · Bloqueante Secreto JWT incompatible entre servicios y fallback falsificable

Evidencia
Backend/Program.cs:90-107 usa Jwt__Secret o el literal cobroup-super-secret-development-key-minimum-32-chars-long. Los secretos Kubernetes del backend operativo solo contienen la conexión; Admin recibe Jwt__Secret. JwtTokenService.cs:130-136 también vuelve silenciosamente al literal si falta o es corto.
Impacto
En ambientes, Admin firma con un valor y Backend valida con otro; las APIs operativas rechazan tokens. Si ambos caen al literal conocido, cualquier persona con el código puede forjar roles/tenant.
Corrección
Fail-fast fuera de Development y distribución segura coherente; preferible validación asimétrica vía autoridad OIDC/JWKS.
Verificación
Token real aceptado por ambos servicios; arranque falla cuando falta material criptográfico.

B-03 · Bloqueante Issuer y audience no se validan

Evidencia
Backend/Program.cs:102-105 y BackendAdmin/Program.cs:108-111 configuran ValidateIssuer=false y ValidateAudience=false aunque definen valores válidos.
Impacto
Cualquier JWT firmado con la clave compartida es aceptado independientemente de emisor o destinatario, ampliando el alcance de una fuga de clave.
Corrección
Activar ambas validaciones y pruebas negativas con issuer/audience erróneos.
Verificación
401 para tokens de emisor o recurso distintos.

B-04 · Bloqueante Refresh tokens de 30 días expuestos en cliente y base de datos

Evidencia
Ambos auth.service.ts:27,57-60,121-141 guardan el refresh token en localStorage. RefreshToken.Token y EfIdentityRepository.cs:129-134 persisten/consultan el valor completo. El contrato anterior declara tokens solo en memoria.
Impacto
Un XSS o lectura de DB obtiene credenciales reutilizables por 30 días.
Corrección
Authorization Code + PKCE/BFF o cookie HttpOnly segura; en servidor almacenar hash con comparación en tiempo constante y revocación familiar.
Verificación
Ningún token largo en Web Storage ni texto claro en DB/logs.

B-05 · Bloqueante Rotación y cambio de tenant no son seguros

Evidencia
JwtTokenService.cs:83-107 lee token activo, guarda uno nuevo y revoca el anterior en operaciones separadas; dos refresh concurrentes pueden emitir descendientes válidos. OrganizationSessionsController.cs:46-73 emite tokens del nuevo tenant sin revocar el refresh anterior y los frontends retiraron la revocación previa.
Impacto
Replay concurrente y continuidad de sesión del tenant anterior, contra el requisito de no reutilizar tokens tras cambio de organización.
Corrección
Rotación atómica con control de concurrencia/familia; revocar toda la familia anterior al cambiar tenant.
Verificación
Dos refresh simultáneos: solo uno prospera; token anterior y descendientes quedan revocados ante replay/cambio.

B-06 · Bloqueante Las rutas frontend de identidad no coinciden con el ingress

Evidencia
Los frontends llaman /identity/api/v1/auth/login. Los ingress envían el prefijo /identity al Admin Backend sin regla de rewrite y la API mapea /api/v1/auth; no existe UsePathBase("/identity").
Impacto
Login, refresh y logout responden 404 en dev/qa/prod aun si el servicio está sano.
Corrección
Configurar rewrite/path-base coherente o runtime config al dominio auth; probar desde ambos hosts PWA.
Verificación
HTTP real por ingress para login, me, refresh y logout.

B-07 · Bloqueante Modelo de identidad aún tiene cambios sin migración

Evidencia
dotnet ef migrations has-pending-model-changes devuelve “Changes have been made to the model since the last migration” aunque existe 20261022135103_AddRefreshTokensTable.
Impacto
El esquema versionado no representa el modelo actual y la funcionalidad de refresh depende de una tabla nueva.
Corrección
Reconciliar modelo/migración/snapshot y revisar el script SQL; incluir job de migración antes del rollout.
Verificación
Comando sin pendientes y migración arriba/abajo sobre PostgreSQL limpio y con datos.

B-08 · Bloqueante Continúa el registro de evidencia sin archivo real

Evidencia
PaymentsController.cs:168-190 conserva POST JSON; PaymentService.cs:283-320 acepta metadatos/ruta del cliente; PaymentEvidence.cs:82-91 usa el hash del contenido vacío.
Impacto
Registros de auditoría falsos y referencias a archivos inexistentes.
Corrección
Eliminar endpoint legado y crear evidencia únicamente desde contenido verificado.
Verificación
Pruebas negativas de metadatos falsificados.

B-09 · Bloqueante Evidencia descargable fuera de ruta y no durable

Evidencia
PaymentsController.cs:142-165 autoriza solo tenant; no valida ruta. LocalFileStorageService.cs:15-16,60-68 escribe en disco del pod; no hay PVC/objeto compartido y producción usa múltiples réplicas.
Impacto
Acceso cross-route y pérdida/404 tras restart o balanceo.
Corrección
Autorización por recurso y almacenamiento privado durable/compartido.
Verificación
Ruta A no lee ruta B; descarga funciona tras restart y desde otra réplica.

B-10 · Bloqueante Excepción de crédito aún acepta plazo distinto

Evidencia
LoanService.cs:112-125 exige monto/tasa exactos, pero solo rechaza duración mayor que ProposedDays.
Impacto
Se origina un préstamo con términos no aprobados.
Corrección
Exigir igualdad en la unidad contractual aprobada.
Verificación
Menor y mayor fallan; solo el plazo exacto prospera.
