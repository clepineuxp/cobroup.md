4. Hallazgos bloqueantes

B-14 · Bloqueante nuevo Todos los bearer válidos pueden fallar por tipo de SecurityToken incompatible

Evidencia
Ambos AccessJwtValidator.cs:29-32 rechazan todo objeto que no sea JwtSecurityToken. Ambos Program.cs usan JwtBearer sin UseSecurityTokenValidators=true. Desde ASP.NET Core 8, el manejador predeterminado entrega JsonWebToken en OnTokenValidated. Las pruebas invocan manualmente JwtSecurityTokenHandler, por lo que no reproducen el middleware.
Impacto
Un access JWT correcto supera firma/issuer/audience y luego es rechazado por el callback; APIs protegidas responden 401 de forma general.
Corrección
Soportar JsonWebToken sin downcast frágil o configurar conscientemente el validador legado; preferir claims del principal y probar el pipeline HTTP real.
Referencia
Microsoft Learn: Security token events return a JsonWebToken.

B-15 · Bloqueante nuevo La precarga y readiness JWKS no comparten la caché usada para autenticar

Evidencia
Program.cs:96-97 registra IJwksValidationService mediante AddHttpClient<T>, que crea un typed client transitorio. Hosted service, configuración JwtBearer y JwksHealthCheck reciben instancias distintas con cachés de instancia separadas.
Impacto
La precarga exitosa no alimenta al resolver de firma. Readiness puede permanecer unhealthy porque su instancia nace sin claves; el primer bearer con un kid válido se rechaza mientras otra instancia refresca en background.
Corrección
Separar HttpClient del almacén de claves y registrar una caché/servicio compartido singleton seguro; precarga, resolver y health deben observar el mismo estado.
Verificación
Test de DI con identidad de instancia/estado, arranque no-Development, readiness verde tras precarga y primer request autenticado exitoso.

B-13 · Bloqueante El Secret RSA renderizado por workflow produce YAML inválido

Evidencia
secret.yaml inserta Jwt__PrivateKeyPem dentro de comillas en una sola línea. La sustitución Python pega el PEM multilínea literalmente. Reproducción auditora con un PEM de prueba: kubectl create --dry-run=client -f - falla con “invalid Yaml document separator”.
Impacto
El pipeline no puede aplicar un Secret real con formato PEM estándar. Kustomize verde antes de sustituir placeholders es un falso positivo de despliegue.
Corrección
Usar bloque YAML correctamente indentado, base64 controlado o Secret montado/gestor externo; validar el manifiesto después de sustituir y sin imprimir la clave.
Verificación
Render post-sustitución con PEM multilínea de prueba, server-side dry-run/namespace limpio y arranque real de Admin Backend.

B-05 · Bloqueante de evidencia La concurrencia PostgreSQL puede aprobar sin ejecutarse

Evidencia
PostgresRefreshTokenConcurrencyTests.cs:30-50 hace return si falta connection string, no conecta o lanza excepción. xUnit lo reporta Passed, no Skipped. Además líneas 134-140 no verifican cuántos descendientes quedan activos ni la revocación final de la familia.
Impacto
No existe evidencia reproducible de que la carrera se ejecutó. El contador 269/269 puede ocultar ausencia total de PostgreSQL.
Corrección
Fallar el gate o marcar Skip explícito cuando la dependencia falta; afirmar estado final: un éxito, cero 500, padre revocado y familia/descendiente según contrato.
Verificación
Salida CI que identifique PostgreSQL usado y assertions completas repetidas varias veces.

B-09 · Bloqueante heredado Evidencias siguen en disco local y QA/producción carecen de configuración

Evidencia
El adaptador sigue siendo LocalFileStorageService; no hay PVC/object storage. Backend exige Storage:EvidencePath fuera de Development, pero los manifests QA/prod no lo definen. Producción mantiene múltiples réplicas.
Impacto
Backend QA/prod falla al iniciar; si se añade una ruta local, persisten pérdida/404 entre réplicas y reinicios.
Corrección
Almacenamiento durable compartido y configuración real por ambiente, con prueba entre réplicas/restart.
Estado
Fuera del alcance del último prompt; permanece abierto correctamente, pero impide aprobación global.

8. Dictamen y siguiente orden

No se recomienda aprobar, mergear ni desplegar este corte. El bloque sí redujo deuda, pero debe pasar otra corrección focal antes de una nueva auditoría.

  1. Resolver B-14 soportando JsonWebToken y agregar prueba HTTP real que acepte un access token válido.
  2. Resolver B-15 con estado JWKS singleton compartido entre precarga, auth y readiness.
  3. Corregir serialización del PEM y validar el YAML posterior a sustitución.
  4. Convertir la prueba PostgreSQL en gate real: Skip visible o fallo, nunca retorno silencioso; completar assertions.
  5. Exigir iat/nbf, eliminar organization_code=DEFAULT y completar pruebas de CSRF/cookie HTTP.
  6. Mantener B-09 y demás hallazgos fuera de alcance como abiertos, sin declarar aprobación global.
Conclusión: avance significativo, pero la autenticación real y el despliegue de claves todavía tienen fallos bloqueantes verificables.
