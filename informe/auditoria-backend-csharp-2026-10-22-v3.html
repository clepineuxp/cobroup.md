3. Qué se realizó bien

Criptografía y separación de responsabilidades

BackendAdmin firma con RS256 y conserva la clave privada; Backend valida por clave pública/JWKS. Se publica kid y existe soporte de clave anterior durante rotación.

Emisión de tokens

Access de 15 minutos y refresh de 30 días, con issuer, audiences separadas, jti, tipo, organización y rol emitidos desde membresía del servidor.

Custodia de refresh

El servidor persiste SHA-256 y no el JWT completo. Los frontends retiraron access/refresh de Web Storage; el access vive en memoria y existe single-flight para refresh.

Autorización y tenant

El login rechaza explícitamente una organización no autorizada. El cambio de organización revoca primero la familia anterior. Descarga/carga de evidencia valida la ruta accesible.

Evidencias de pago

El endpoint JSON legado fue retirado; la carga usa streaming con límite de 10 MB, inspección de firma, SHA-256 y compensación del archivo si falla la persistencia.

Dominio y trazabilidad

La excepción de crédito exige el plazo exacto aprobado. El correlation ID se propaga en clientes HTTP de ambos backends.

Migraciones

Ambos modelos reportan cero cambios pendientes y fue posible generar scripts idempotentes. La migración nueva retira las tablas heredadas del mecanismo anterior.

Calidad automatizada

232/232 pruebas pasan; ambos frontends construyen; no se detectaron vulnerabilidades conocidas en dependencias productivas NuGet/npm con las fuentes consultadas.

4. Hallazgos bloqueantes

B-05 · Bloqueante La rotación concurrente no tiene garantía demostrada de cierre seguro

Evidencia
EfIdentityRepository.cs:158-202 usa RepeatableRead, lectura seguida de actualización, sin bloqueo de fila explícito ni token de concurrencia. La prueba JwtTokenServiceTests.cs:127-178 usa un repositorio en memoria y ejecuta refresh secuencial, no dos requests simultáneas sobre PostgreSQL.
Riesgo
Ante la carrera, PostgreSQL puede abortar una transacción por serialización; no hay manejo que la convierta en rechazo controlado y revocación familiar. El perdedor puede terminar en 500 y no queda demostrada la reacción requerida ante replay concurrente.
Requisito
Decisión JWT 2.2 y prueba mínima 4: un solo descendiente válido y revocación de la familia comprometida.
Cierre
Prueba de integración PostgreSQL real con barrera concurrente, resultado HTTP determinista, un único descendiente y estado final de toda la familia verificado.

B-06 · Bloqueante Cookie y rutas externas impiden completar el flujo real por ingress

Evidencia
AuthController.cs:165-192 y OrganizationSessionsController.cs:80-92 emiten __Host-cobroup-refresh y fallback con Path=/api/v1/auth. Los navegadores exigen Path=/ para prefijo __Host-. Además, la solicitud externa es /identity/api/v1/auth/*, que tampoco coincide con el path del fallback. El frontend operativo configura contexto /api/v1/session/me, mientras el ingress solo enruta al backend bajo /api/operations.
Impacto
El navegador puede rechazar la cookie host y no enviará el fallback a refresh/logout/cambio de tenant; el login operativo falla al cargar contexto aunque haya recibido un access token.
Corrección
Alinear Path público y reescritura, usar correctamente __Host- o un nombre/path coherente, y hacer enrutable el endpoint de contexto operativo.
Verificación
Prueba con navegador real por cada host de dev/qa/prod: login → me → refresh → cambio de organización → logout, inspeccionando Set-Cookie y envío efectivo.

B-11 · Bloqueante La API acepta JWT firmados sin exigir todo el contrato de claims

Evidencia
JwksValidationService.cs:64-75 valida firma, RS256, issuer, audience y tiempos, pero no exige explícitamente typ=access, sub, jti, iat, organization_code y role. Las políticas en Backend/Program.cs:112-126 solo exigen autenticación y organization_id para usuario general. BackendAdmin repite el patrón en Program.cs:46-60.
Impacto
Un token correctamente firmado y destinado a cobroup-api, pero incompleto o de tipo incorrecto, puede superar autenticación/política de usuario. Emitir claims correctamente no equivale a validarlos estrictamente.
Corrección
Validación central de tipo y claims obligatorios, formato GUID, rol permitido, kid presente y coherencia temporal; rechazo antes de autorización.
Verificación
401 individual para cada claim ausente/malformado, typ incorrecto, kid ausente/desconocido, algoritmo, expiración y nbf inválidos.

B-12 · Bloqueante La protección CSRF está registrada, pero no se aplica

Evidencia
BackendAdmin/Program.cs:62-69,211-214 registra antiforgery y middleware; ningún método de refresh, logout o cambio de organización declara validación antiforgery. Ambos auth.service.ts:72-104,124-130 no solicitan /antiforgery ni envían X-XSRF-TOKEN.
Impacto
Las operaciones mutables basadas en cookie carecen del control explícitamente requerido. La mera presencia de UseAntiforgery no añade validación a endpoints sin metadata/filtro.
Corrección
Exigir antiforgery en refresh, logout y cambio de organización; obtener/renovar token en ambos frontends y enviar cabecera. Definir comportamiento tras expiración.
Verificación
403/400 sin token o con token incorrecto; éxito con par cookie/cabecera válido, incluyendo flujo por ingress.

B-13 · Bloqueante GitOps continúa configurando el mecanismo retirado y QA/producción no arrancan

Evidencia
dev|qa|prod/admin-backend/secret.yaml:13 define Jwt__Secret; workflows usan *_JWT_SECRET. No se suministran Jwt__PrivateKeyPem/Path, Jwt__KeyId ni audiences. En QA/producción RsaKeyService.cs:35-55 falla al construir. Backend exige Storage:EvidencePath fuera de Development (Program.cs:53-56) y ningún manifiesto lo define.
Impacto
Admin Backend y Backend operativo entran en CrashLoop antes de servir; el pipeline sustituye un secreto que el runtime nuevo ya no consume.
Corrección
Actualizar Secret/ConfigMap y workflows para material RSA por ambiente, kid, issuer, audiences, JWKS y almacenamiento; validar placeholders vacíos antes de copiar/aplicar.
Verificación
Despliegue desde namespace limpio en QA y producción, pods Ready, llave privada solo en Admin, JWKS alcanzable y Backend aceptando/rechazando tokens reales.

B-09 · Bloqueante Evidencias todavía se almacenan en disco local no compartido

Evidencia
LocalFileStorageService.cs:15-16,84-98 escribe al filesystem local. Los manifests no montan PVC ni configuran object storage; producción declara dos réplicas. La autorización cross-route sí fue corregida.
Impacto
Una descarga puede caer en otra réplica y responder 404; restart/reprogramación puede perder archivos. Definir una ruta local no la convierte en almacenamiento durable compartido.
Corrección
Adaptador privado de object storage o volumen compartido compatible con réplicas, cifrado/retención, health operativo y política de compensación.
Verificación
Cargar en réplica A, descargar en B, reiniciar/reprogramar y verificar integridad SHA-256 y autorización de ruta.

8. Dictamen y orden de remediación

Se mantiene el estado NO APROBADO. No se recomienda commit de cierre, merge ni despliegue como versión JWT conforme.

  1. P0: corregir ruta/cookie externa y endpoint de contexto; aplicar CSRF completo en API y frontends.
  2. P0: adaptar GitOps a claves RSA, kid, audiences, JWKS y almacenamiento durable; eliminar el secreto HMAC retirado.
  3. P0: exigir tipo y todos los claims del contrato en ambos backends.
  4. P0: demostrar rotación/replay concurrente sobre PostgreSQL real con respuesta controlada.
  5. P1: cerrar JWKS, revocación no validada, rate limit, proxies, migración/readiness y cero warnings.
  6. P1: ejecutar la matriz end-to-end completa en dev/qa/prod y adjuntar evidencia reproducible.
